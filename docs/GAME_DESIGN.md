# 게임 기획서 (초안 v0.1)

한국프로농구(KBL) 구단 GM 시뮬레이션 + 카드 수집·육성. 웹 / 싱글 플레이.

> 상태: 초안. 아래 수치와 이름은 모두 **제안값(예시)** 이며 플레이 테스트로 조정한다.
> 이 문서는 사람과 AI 에이전트 모두의 기준 문서다. 규칙을 바꾸면 코드보다 먼저 이 문서를 고친다.

## 1. 한 줄 요약

KBL 10개 구단 중 하나를 맡아 선수 카드를 모으고 키우며, 이적 시장과 라인업을 운영해 시즌을 치르는 싱글 플레이 웹 게임.

## 2. 설계 기둥

1. **육성이 중심, 수집이 동기**: 새 선수를 얻는 재미와 한 선수를 키우는 재미가 서로를 받쳐준다.
2. **직접 조작 경기 없음**: 라인업과 전술을 정하면 시뮬레이션이 결과를 계산한다. 선택의 결과가 숫자로 설명되어야 한다.
3. **작게 시작**: MVP는 1시즌, 저장 기능, 단순한 이적까지만. 에셋과 기능은 그다음에 늘린다.

## 3. 코어 루프

```
선수 획득(드래프트/FA/트레이드) → 훈련·육성 → 라인업 편성 → 경기 시뮬레이션
        ↑                                                      ↓
   다음 시즌 ← 계약·재정 정산 ← 시즌 보상·성장 ←←←←←←←←←←←←←←←←┘
```

한 번의 "턴" = 하루 일정(훈련 또는 경기). 한 시즌 = 정규리그 54경기(10개 구단 6라운드) + 시즌 종료 정산·이적 시장. 54경기는 일괄 시뮬레이션으로 빠르게 넘길 수 있게 한다.

플레이어는 아래 10개 구단 중 하나를 선택한다. (2026-27시즌 참가 구단 기준. 연고지 명칭 변경은 공식 사이트에서 확인 필요)

| 구단 | 연고 |
|---|---|
| 원주 DB | 원주 |
| 서울 삼성 | 서울 |
| 고양 소노 | 고양 |
| 서울 SK | 서울 |
| 창원 LG | 창원 |
| 안양 정관장 | 안양 |
| 부산 KCC | 부산 |
| 수원 KT | 수원 |
| 대구 한국가스공사 | 대구 |
| 울산 현대모비스 | 울산 |

**실명 사용 원칙**
- 구단 이름과 연고지는 실제 것을 쓴다. 구단 로고와 공식 엠블럼은 쓰지 않는다(팀 컬러와 텍스트 이름만).
- **선수 이름은 실명을 쓸 수 있다.** 단, 개인·지인 소규모 플레이(비상업)용이다. 능력치·잠재력·계약은 실제 수치가 아니라 이름을 시드로 한 **가상 값**이다.
- 기본 데이터는 전원 가상 선수이고, 실명은 `data/rosters/<구단id>.csv`로 넣으면 반영된다(`data/rosters/README.md` 참고). 실제 로스터는 공식 자료로 사람이 확인해서 채운다. 에이전트가 검색 결과로 추측해 채우지 않는다.
- **선수 이미지는 실제 사진을 가져와 쓰지 않는다.** 사진은 촬영자·KBL·구단의 저작물이다. 이미지는 직접 가진 파일을 `assets/portraits/<선수id>.png`에 넣거나, 실존 인물과 닮지 않은 스타일화된 카드 일러스트를 쓴다.
- 링크를 불특정 다수에게 공개하거나 수익 요소를 넣게 되면 KBL·구단·선수 측 이용 허락을 별도로 확인한다.

### 4.2 규정 (2026-27시즌 검색 기준, 구현 전 공식 확인 필요)

| 항목 | 내용 |
|---|---|
| 국내 선수 샐러리캡 | 30억 원 |
| 외국 선수 샐러리캡 | 100만 달러 (1인 상한 70만 달러) |
| 외국 선수 | 구단당 2명 보유, 2명 출전. 2·3쿼터는 2명 동시 출전 가능, 1·4쿼터는 1명만 출전 |
| 정규리그 | 10개 구단, 54경기 |
| FA | 시즌 종료 후 협상 시작. FA로 타 구단 이적 시 연내 이적 제한 규정은 폐지됨 |
| 드래프트 | 신인 드래프트 + 해외 3년 이상 경력 선수 특별 드래프트(구단이 같은 확률로 지명) |
| 트레이드 | 세부 규정을 확인하지 못함. 아래 5.4의 게임용 단순 규칙을 사용 |

게임에서는 이 규정을 **설정 파일 하나**(`league-rules.json`)에 모아, 규정이 바뀌어도 코드 수정 없이 반영한다.

## 5. 핵심 시스템 (MVP)

### 5.1 선수

| 항목 | 설명 |
|---|---|
| 기본 정보 | 이름, 포지션(PG/SG/SF/PF/C), 나이, 등번호 |
| 능력치 | 슛, 패스, 수비, 리바운드, 운동능력, 체력 (각 0~99) |
| OVR | 포지션별 가중 평균으로 계산한 종합 점수 |
| POT | 성장 상한. 육성 한계를 정한다 |
| 희귀도 | 일반 / 레어 / 에이스 / 레전드 (카드 프레임·성장 상한과 연결) |
| 구분 | 국내 / 외국 선수 (캡과 출전 규정이 다르다) |
| 계약 | 연봉(억 원), 남은 계약 기간 |
| 상태 | 컨디션, 부상 여부 |

### 5.2 육성

- 훈련 슬롯에 선수를 배치하고 능력치를 선택하면 경기 일정 사이에 경험치가 쌓인다.
- 성장 속도는 나이와 POT에 따라 달라진다. 어릴수록 빠르고, 상한(POT)에 가까울수록 느려진다.
- 과훈련은 컨디션을 깎아 경기력에 영향을 준다.

### 5.3 수집

- 시즌 종료 후 **신인 드래프트**: 후보 카드를 보고 순번에 따라 지명한다. 후보 풀과 지명 순번은 시즌 성적과 연동한다.
- 선수 카드의 희귀도와 성장 상한(POT)이 수집의 목표가 된다.
- 확률형 뽑기는 MVP에서 제외하고 선택형 획득으로 시작한다.

### 5.4 이적 (MVP에 포함)

| 방식 | 규칙(게임용 단순화) |
|---|---|
| **FA 영입** | 시즌 종료 후 계약이 끝난 선수가 시장에 나온다. 플레이어와 AI 구단이 같은 시장에서 경쟁하고, 선수는 연봉, 팀 성적, 출전 기회를 보고 선택한다. |
| **트레이드** | 플레이어가 선수 교환(필요 시 현금 포함)을 제안한다. AI 구단은 선수 가치(OVR, POT, 나이, 계약)를 점수로 평가해 수락·거절한다. 양쪽 모두 샐러리캡을 지켜야 성립한다. |
| **방출·계약 해지** | 남은 연봉 일부를 위약금으로 지불한다. |
| **외국 선수 교체** | 부상이나 부진 시 외국 선수 시장에서 교체 영입한다. 외국 선수 캡 안에서만 가능하다. |

- AI 구단도 같은 규칙으로 이적한다. 시즌 종료 후 이적 시장 기간에 AI 구단 간 FA 계약이 일어난다.
- "AI 구단이 얼마나 똑똑하게 거래하는가"가 난이도를 정한다. MVP는 단순한 가치 평가식으로 시작한다.
- 한 번에 구현하지 않고 FA → 트레이드 → 외국 선수 교체 순으로 넣는다.

### 5.5 경기 시뮬레이션

- 입력: 스타팅 5인 + 전술 설정(템포, 공격 성향, 수비 방식) + 선수 컨디션.
- 출력: 최종 점수, 선수별 기록(득점·리바운드·어시스트), 승패.
- 목표: 같은 입력이라도 무작위 요소 때문에 결과가 달라지되, 능력치 차이가 크면 승률이 확실히 오른다.
- 시뮬레이션 코드는 화면과 분리해 **순수 함수**로 만든다(테스트와 밸런스 검증이 쉬워진다).

### 5.6 경제

- 재화: 구단 자금 하나로 시작한다. 국내 선수 연봉 총액은 30억 원 캡을, 외국 선수는 100만 달러 캡을 넘을 수 없다.
- 수입: 경기 승리 보상, 시즌 성적 보너스. 지출: 선수 연봉, 훈련 비용.
- 샐러리캡이 "좋은 선수만 모으기"를 막는다. 연봉 수치는 억 원 단위로 통일한다.

## 6. 화면 구성 (MVP)

1. **홈**: 구단 현황(자금, 순위, 다음 경기)
2. **로스터**: 선수 목록 표(OVR, 포지션, 연봉), 정렬·필터
3. **선수 상세**: 카드 + 3D 뷰어(프로토타입 재사용), 능력치, 계약, 성장 기록
4. **라인업·전술**: 스타팅 5인 편성, 전술 설정
5. **경기 결과**: 박스스코어와 요약
6. **드래프트·이적 시장**: FA 목록, 트레이드 제안, AI 구단 거래 내역
7. **리그**: 10개 구단 순위, 일정
8. **설정·저장**

## 7. 데이터 구조 초안

선수·구단·규정 데이터는 코드와 분리된 JSON(`players.json`, `teams.json`, `league-rules.json`)으로 관리해 밸런스 조정을 쉽게 한다. 기본은 가상 선수이고, 실명 로스터는 CSV로 덮어쓸 수 있다(`real` 필드로 구분).

```json
{
  "id": "p001",
  "name": "예시 선수",
  "position": "PG",
  "age": 19,
  "number": 7,
  "real": false,
  "rarity": "rare",
  "stats": { "shooting": 62, "passing": 70, "defense": 55, "rebound": 40, "athletic": 66, "stamina": 68 },
  "potential": 84,
  "origin": "domestic",
  "teamId": "busan-kcc",
  "contract": { "salaryEok": 1.2, "yearsLeft": 3 },
  "assets": { "portrait": "assets/portraits/p001.png", "model": null }
}
```

## 8. 기술 방향 (제안)

- **웹, 서버 없음**: 정적 사이트로 시작. 저장은 브라우저 로컬 저장소(`localStorage`).
- 게임 로직(시뮬레이션, 성장, 경제)은 UI와 분리된 순수 모듈로 작성하고 단위 테스트를 둔다.
- 3D 선수 뷰어는 three.js (이미 프로토타입 있음).
- 언어와 프레임워크는 개발 에이전트와 함께 결정한다(작은 규모라 단순한 구성을 우선).

## 9. 에셋 파이프라인

| 단계 | 도구 | 비고 |
|---|---|---|
| 선수 2D 카드 이미지 | Canva `generate-image` | 스타일 가이드(색, 시점, 선 굵기)를 프롬프트에 고정 |
| 배경 제거 | Canva `remove-background` | 투명 PNG로 저장 |
| 3D 모델 | Weave (Meshy/Tripo/Hunyuan) → `.glb` | 크레딧 소모가 크므로 **대표 선수·레전드 카드에만** 사용 |

MVP 원칙: 모든 선수는 2D 카드로 시작하고, 3D는 선택 기능으로 둔다.

## 10. AI 에이전트 운영 (초기 2~3역할)

| 역할 | 맡는 일 | 산출물 |
|---|---|---|
| 기획·밸런스 | 이 문서 관리, 능력치 공식, 경제 수치 검증 | 문서 변경, 밸런스 표 |
| 개발 | 기능 구현, 시뮬레이션 코드, 테스트 | 브랜치와 PR |
| 에셋 | 이미지·3D 생성, 파일 정리 | `assets/` 파일 |

운영 규칙(제안): 기능 단위로 브랜치와 PR을 만들고, 병합 전에 사람이 확인한다. 역할은 필요할 때만 늘린다.

## 11. 열린 질문

- 시즌 길이와 한 턴의 단위(하루 vs 주)
- 선수 성장 곡선(나이별 증가폭)의 구체적 수치
- 확률형 요소를 나중에 넣을지 여부
- 게임 이름과 아트 스타일(현재 캐릭터는 반실사 일러스트 풍)
- 별도 저장소로 분리할지 (현재는 연습용 `first-pr-practice` 저장소에 임시로 둠)
- KBL 트레이드의 실제 규정(검색으로 확인하지 못함)과 게임용 단순화 수준
- 10개 구단 × 약 14명(국내 12 + 외국 2) = 약 140명의 가상 선수를 어떻게 생성할지(절차적 생성 규칙)
- 구단 이름 사용에 대한 KBL·구단 측 허락이 필요한 시점(공개 배포 여부)
